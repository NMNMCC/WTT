# WTT Architecture Overview

The WTT architecture is built around two core components: the **Peer Client**
and the **Signaling Server**. Its communication model operates on two distinct
planes:

1. **Signaling Plane**: This is a persistent **WebSocket** connection
   established between a client and the signaling server. This channel does
   _not_ carry any application data. It is used exclusively for authentication,
   peer discovery, service advertisement, and exchanging metadata (SDP and ICE
   Candidates) during connection setup.
2. **Data Plane**: This is a direct peer-to-peer (P2P) connection established
   between clients using a **WebRTC DataChannel**. All end-user application
   traffic (TCP/UDP data) is transmitted with end-to-end encryption over this
   channel.

A single WTT client instance can act as both a **Provider** and a **Consumer**.
Internally, the client maintains a separate `RTCPeerConnection` instance for
each tunnel—whether it's providing or consuming a service—ensuring that each
tunnel is isolated and managed independently.

## Signaling Channel Design (Client ↔︎ Server)

### Authentication Flow

For security and flexibility, clients do not use long-lived user tokens to
establish the WebSocket connection directly. Instead, a two-step authentication
process is used:

1. **Obtain a Session Token (JWT)**: On startup, the client makes a standard
   **HTTPS RESTful** API call (`POST /api/v1/auth`), sending its long-lived user
   token to the signaling server in exchange for a short-lived session token
   (JWT).
2. **Upgrade to WebSocket**: The client then initiates the WebSocket connection
   request, including the JWT obtained in the previous step in the
   `Authorization` HTTP header: `Authorization: Bearer {{jwt.token}}`. The
   server validates this JWT before upgrading the connection to the WebSocket
   protocol.

### Message Envelope

To simplify parsing and routing, all messages exchanged over the WebSocket are
wrapped in a standardized `Envelope` structure.

```json
{
  "id": "unique-message-id-c1", // Unique message ID for tracking and replies
  "type": "event-type",         // The type of event
  "target_peer_id": "peer-id-b",  // Required only when forwarding a message
  "payload": { ... }            // The specific payload for the event
}
```

- **`id`**: A unique identifier (e.g., UUID or nanoid) generated by the message
  originator. The server includes this `id` in its replies, allowing the client
  to correlate responses with their original requests.
- **`type`**: The core event type, which determines the structure of the
  `payload` and the server's resulting action.
- **`target_peer_id`**: This field is required when a client needs to send a
  message to another specific client (e.g., for forwarding SDP or ICE
  candidates).
- **`payload`**: The actual content of the message.

### Primary Events

| `type`               | Originator | Target | `payload` Example                                     | Description                                                                                                                    |
| :------------------- | :--------- | :----- | :---------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------- |
| `register`           | Client     | Server | `{}`                                                  | After a successful WebSocket connection, the client sends this to register itself and receive its unique `PeerID`.             |
| `publish_services`   | Client     | Server | `{"services": ["db", "api"]}`                         | A **Provider** client sends this to advertise the list of services it offers.                                                  |
| `request_connection` | Client     | Server | `{"target_peer_id": "B", "service_name": "db"}`       | A **Consumer** client sends this to request a connection to the `db` service offered by Peer B.                                |
| `signal`             | Client     | Peer   | `{"to_peer_id": "B", "data": {"type": "offer", ...}}` | Wraps an SDP offer/answer or an ICE candidate and asks the server to forward it to another peer.                               |
| **`reply`**          | Server     | Client | `{"success": true, "reply_to": "c1", "data": ...}`    | A **generic reply** from the server to a client's request. The `success` field indicates whether the operation was successful. |

## Detailed WebRTC Connection Flow (Client ↔︎ Client)

The following is a complete and precise breakdown of the steps required to
establish a WebRTC DataChannel, including the critical **ICE Candidate**
exchange process.

1. **Initiator (Peer A / Consumer) Prepares the Offer**:

   1. Peer A creates a new `RTCPeerConnection` object.
   2. Peer A calls `createDataChannel()` to create the data channel on the
      connection.
   3. Peer A calls `createOffer()` to generate the SDP `offer`.
   4. Peer A calls `setLocalDescription(offer)`. **This action triggers the
      local ICE agent to start gathering candidates**.
   5. Peer A sets up a listener for the `onicecandidate` event. As each new ICE
      candidate is gathered, it is sent to Peer B via the signaling server using
      a `signal` event.
   6. Peer A sends the `offer` to Peer B via the signaling server, packaged
      within a `signal` event that also includes WTT metadata like
      `{"service_name": "db"}`.

2. **Receiver (Peer B / Provider) Processes the Offer and Prepares the Answer**:

   1. Peer B receives the `offer` and metadata from Peer A (forwarded by the
      server).
   2. **Connection Decision**: Peer B inspects the `service_name` in the
      metadata to determine if it is a service it is configured to provide. If
      not, it sends a rejection message back through the signaling server.
      Otherwise, it proceeds.
   3. Peer B creates its own `RTCPeerConnection` object.
   4. Peer B calls `setRemoteDescription(offer)` to set Peer A's description.
   5. Peer B calls `createAnswer()` to generate the SDP `answer`.
   6. Peer B calls `setLocalDescription(answer)`. **This action also triggers
      its ICE agent to begin gathering candidates**.
   7. Peer B listens for the `onicecandidate` event and sends each gathered ICE
      candidate to Peer A through the signaling server as it becomes available.
   8. Peer B sends the completed `answer` back to Peer A via a `signal` event.
   9. Peer B sets up a listener for the `ondatachannel` event, which will fire
      when Peer A's data channel is established on its end.

3. **Connection Establishment and Completion**:

   1. Peer A receives the `answer` from Peer B and calls
      `setRemoteDescription(answer)`.
   2. Throughout this process, both peers continuously receive ICE candidates
      from each other and add them to their respective `RTCPeerConnection`
      instances by calling `addIceCandidate()`.
   3. The ICE agents on both sides use the exchanged candidates to test for a
      viable P2P path. Once a path is successfully established, the
      `RTCPeerConnection` state transitions to `Connected`.
   4. At this point, Peer B's `ondatachannel` event is triggered, giving it
      access to the data channel instance.
   5. The `DataChannel`'s state on both ends transitions to `open`, and
      bidirectional communication is now established.
